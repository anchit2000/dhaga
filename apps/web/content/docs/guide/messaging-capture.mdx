Dhaga can capture people straight from a chat you already have open. **Forward
a contact card, a note, or a photo** to the Dhaga bot on **WhatsApp** or
**Telegram**, reply **`DONE`**, and Dhaga creates and tags the contact, keeps
every forwarded message as a **receipt**, and replies with a summary. It's the
fastest way to capture from your phone without any app install — hand someone's
card straight into your graph while you're still standing at the booth.

This is a **core, fully self-hostable** feature — it needs no cloud tier. Setting
up the bot (the webhook, the API keys) is a one-time admin job covered in
[Self-hosting](/docs/self-hosting); this page is about *using* it once a channel
is connected.

## Connecting your chat

There's one bot per deployment, so Dhaga has to know which account a chat
belongs to before it saves anything.

1. Open **Settings → Messaging** (`/app/settings`).
2. Generate a **link token** — a short, single-use code that expires in a few
   minutes.
3. **Scan the QR with your phone**, one per channel:
   - **Telegram** opens the bot with a **Start** button — tap it and you're
     linked. The code travels in the link, so there's nothing to type.
   - **WhatsApp** opens a chat with the code already in the message box — just
     hit send.

   On a phone you can tap the code instead of scanning it. Prefer to do it by
   hand? Copy the token and send it to the bot as an ordinary message — that
   still works exactly as before.

From then on, anything you forward from that chat lands in *your* graph. A chat
that isn't linked yet gets a friendly nudge back explaining how to link it.

<Callout title="Self-hosting for one person">
On a single-owner self-hosted instance, an unlinked chat falls back to the
owner automatically (set by `DHAGA_OWNER_EMAIL`), so you can start forwarding
before wiring up per-user linking.
</Callout>

## What you can forward

- **Contact card** — a shared vCard is imported from its own fields (name,
  numbers, org), never re-read as text, so nothing is lost in translation. A
  card for someone a note already mentioned fills that person in instead of
  duplicating them.
- **Text** — a message you type or forward becomes a note, and Dhaga
  auto-extracts facts from it, each with a receipt back to the message.
- **Photo** — a business card or badge is scanned into a contact; a photo that
  *isn't* a card (a whiteboard, a poster, a conference schedule, a society
  noticeboard) is read as text and kept as a note. Send a caption with it and
  the caption becomes a note on that person. **The photo itself is kept too**,
  alongside the text read off it, so you can always check the reading against
  the original — unless you've turned photo storage off in
  [Settings](/docs/guide/settings), which governs forwarded photos exactly as it
  governs a card scan. Delete the note and its photo goes with it.
- **Location** — kept as a note on the current contact.

Anything else — a **voice note** (see below), a video, a document, a sticker, an
empty message — gets a reply telling you so. Nothing is ever dropped in silence:
if an item can't be saved, either the bot answers straight away or the batch
summary lists what it skipped and why.

## How a batch works

Order matters, but **naming a person beats order**:

- A **contact card or photo** sets the *current contact*.
- **Text that names someone** is filed on that person — matched to whoever is
  already in your graph, or created if nobody matches — even when a different
  card came first. A note about Bob never lands on Alice just because Alice's
  card arrived earlier.
- **Text that names nobody** ("wants intros to fintech founders") falls back to
  the current contact. That one is a guess, and the summary labels it as such.
- A leading **text with no card** establishes the contact on its own, the same
  way pasted text does in [quick-add](/docs/guide/capturing-people).
- Forward **several cards** in one batch and you get several contacts.

**Telling the bot what to do is not a note.** A message like *"create a new
contact"* or *"save this under Acme"* is read as an instruction, so it isn't
stored in anyone's timeline and no follow-ups are invented from it. If it names
who the capture is about and nothing has been saved yet, that name is what the
new contact is called. Anything carrying real information stays a note, even
when it reads like a command to yourself — *"call Priya on Tuesday"* is a note,
and still becomes a follow-up.

**A capture that names no person still gets a usable name.** A noticeboard or
an office directory has an organisation on it but nobody in particular, so the
contact is named after the organisation rather than saved blank — a nameless
contact can't be found by search later. If there's no organisation either, it's
saved as *"Unnamed contact"* for you to rename.

Where the source says **whose** number or address each one is — *"Society office
– 7507626215"*, *"MNGL – 9764648750 (Navnath)"*, *"admin@…"* — those labels are
kept on the contact's phone and email entries instead of arriving as an
anonymous list.

## When Dhaga isn't sure who you mean

If a forwarded note could be about more than one person in your graph — two
Rohans, say — Dhaga does **not** guess and does **not** interrogate you in chat.
It raises the note in your **Inbox**, where you pick who it belongs to:

```
This note could be about more than one "Rohan". Which one did you mean?
  [ Rohan Mehta · STPI ]   [ Rohan Iyer · Infosys ]   [ New person ]
```

The note travels *inside* that confirmation, so nothing is written to anybody
until you choose — and nothing can be lost if you never do. Each ambiguous note
gets its own entry, so a batch that raises five of them gets five, and the batch
summary tells you how many are waiting.

A note that matches exactly one person is attached to them silently — no
confirmation, and no duplicate contact.

## Closing a batch

You never have to remember to finish — a batch is saved three ways, and nothing
is ever lost:

1. **Reply `DONE`** (or `finish`, `end`, `/done`) to save immediately.
2. **Start a new forward** and any earlier open batch is saved first.
3. **Walk away** — an idle batch auto-saves after 24 hours of quiet (self-hosters
   can tune this with `DHAGA_MESSAGING_IDLE_MINUTES`).

A batch also stops accepting forwards once it holds 10 unsaved items
(`DHAGA_MESSAGING_MAX_OPEN_ITEMS`). The bot says so rather than swallowing the
message: the longer a batch runs, the more notes it has to file by assumption, so
it asks you to close it while you still remember who each one was about.

When a batch is saved, the bot replies with a summary of who and what it stored —
including **where each note went and why**: whether the note named that person,
whether it created them because nobody matched, or whether it was *assumed* to be
about them because the note named nobody at all. Assumptions are the ones worth
skimming; fix any of them in Dhaga.

<Callout title="Voice notes aren't supported yet">
Forward a voice note and the bot replies *"Voice notes aren't supported yet —
coming soon! For now please type it, send a photo, or forward a contact."* — it
is never quietly swallowed. Server-side transcription is a pluggable gateway
that ships with **no provider**, and the refusal is gated on that gateway: the
day a provider is configured, voice notes start being transcribed and attached
like any other note, with no further change. (This is separate from **Dhaga
Voice**, the on-device dictation in web
[quick-add](/docs/guide/capturing-people) — that one does transcribe.)
</Callout>

## More channels later

WhatsApp and Telegram ship today, but the messaging layer is provider-agnostic:
it mirrors Dhaga's [LLM and search gateways](/docs/extending), so a new channel
is a self-contained plug-in with no changes to the capture flow above. If you
self-host, see [Self-hosting](/docs/self-hosting) for the per-channel setup.
